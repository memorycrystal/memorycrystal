Available on hosted HTTP MCP and stdio MCP.

Call `crystal_health` with no arguments. The optional `limit` argument is deprecated and ignored.

## When to use

Use health to check that your credentials reach the service and an authenticated database read succeeds. Use [stats](/tools/stats) for counts, and a small [recall](/tools/recall) request to inspect actual retrieval behavior.

GET or POST `/api/mcp/health` returns `ok`, `computedAt`, `status`, `version`, `readiness`, `checks`, `planes`, and `build`. A successful response reports `status: "alive"` and an authenticated database read.

Provider, vector, capture, and recall readiness can remain `unknown` or `not_probed`. Liveness does not establish that embedding or distillation will succeed. The response's version is a reported health value; do not use it as a universal component-version inventory.

This check does not scan memories or produce a hygiene worklist. Use [stats](/tools/stats) for account counts.

## Parameters

| Parameter | Behavior |
| --- | --- |
| `limit` | Optional deprecated argument; ignored |

### Deep mode (raw HTTP only)

`GET /api/mcp/health?deep=1`, or `POST /api/mcp/health` with `{"deep": true}`, also probes what a recall needs. It runs a query embedding on a fixed probe phrase, a one-result vector search on your memory index that returns no memory content, and, when a rerank model is configured, one answer-check call to that model over fixed synthetic candidates. The rerank probe passes only when the reply is the JSON recall's answer check accepts; any other reply fails it with reason `invalid_response`. Each probe has a 2.5 second timeout (the embedding and rerank requests are cancelled when it expires; the vector search is not, so its timeout only stops the wait) and reports `status` (`passed`, `failed`, `timeout` or `skipped`), `ms` and, on failure, a short `reason`.

`readiness` is then `ready` (every configured probe passed), `degraded` (recall works without the rerank stage) or `not_ready` (semantic recall cannot run), and `planes.recall` reports the same as `ready`, `degraded` or `failed`. Deep probes make paid provider calls on your account. They are limited to 2 per API key per minute, separately from the ordinary rate limit; the default response is unchanged and stays cheap.

```json
{
  "status": "alive",
  "readiness": "ready",
  "checks": {
    "authenticatedDatabaseRead": "passed",
    "embeddingProvider": "passed",
    "recallEmbedding": { "status": "passed", "ms": 310 },
    "recallVectorSearch": { "status": "passed", "ms": 42 },
    "recallRerank": { "status": "skipped", "ms": 0, "reason": "not_configured" }
  },
  "planes": { "capture": "not_probed", "recall": "ready" }
}
```

## Interpret readiness

`alive` confirms this limited authenticated check. `not_probed` means the check did not test that component, and `unknown` is not a failure verdict. Check the affected operation when troubleshooting capture, embeddings, or distillation.

## Errors and common mistakes

A 401 means you must correct the credential; a 429 means you should wait according to [rate-limit guidance](/api/rate-limits). Do not interpret liveness as an end-to-end retrieval test or a complete version inventory.
